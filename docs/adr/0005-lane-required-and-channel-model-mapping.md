# ADR 0005：车道是唯一路由入口，改名回到渠道级 model_mapping

- 状态：已采纳
- 依据：`docs/design-v1.md` §3.1、§7.1、§7.7；`docs/routing-spec-v1.md` §1
- 取代：ADR 0001 中"隐式链零配置可路由"部分

## 背景

ADR 0001 让"渠道声明即自动成链"：任何被渠道声明的模型无需配置即可调用，
改名下沉到车道成员的 `upstream_model`。落地后发现两个与自用网关目标相悖的后果：

1. **无法保证"每个模型都经过规划好的故障链"**。隐式链按渠道 priority 自动成形，
   运维以为"这个模型只打 A、再打 B"，实际只要 C 也声明了该模型就会被排进去。
   要控制就得逐个模型建车道，而"没建也能用"让人没有动力去建，配置漂移且不可审计。
2. **上游命名不一致时逐个成员改名太散**。同一上游渠道提供的多个模型往往统一带前缀/
   后缀（如 `vendor-a/model-1`），在每条车道的每个成员里各写一遍既重复又易漏。

## 决策

1. **车道是唯一路由入口**：请求模型名存在同名启用车道才可调用；没有车道一律
   `503 No available channel for model <X>`（与"上游全挂"同形，见 ADR 0001）。
   删除隐式成链。
2. **渠道新增 `model_mapping`**（JSON dict：**模型名 → 上游真名**），在渠道管理里配置一次。
3. **成员上游名解析**：`Channel.ModelMapping[成员所选模型] ?? 成员所选模型`。
   ~~成员级 `upstream_model` 显式覆盖~~ **已由 [ADR 0008](0008-member-stores-selected-model.md) 移除**：
   成员只存所选模型，上游改名只保留渠道映射这一层。
4. ~~**一键固化**：`POST /api/lanes/seed` 为所有"渠道已声明但无车道"的模型按渠道
   `priority` 生成 `failover` 车道（成员 `upstream_model` 留空 → 用渠道映射）。
   一键固化不属于当前产品范围。~~
   **已撤销（后续变更）**：产品要求路由只支持手动，`POST /api/lanes/seed` 已从代码、
   文档与测试中整体移除。建车道统一走 `PUT /api/lanes/{name}`（控制台路由页「新建车道」，
   可输入任意路由键，含没有任何渠道声明的自定义名）。

## 后果

- 优点：路由入口单一，模型能否调用、按什么顺序调用完全由车道决定；上游改名在渠道
  配置一次（ADR 0008 兑现了这一点——此前成员级覆盖会让映射改动失效）；
  `GET /api/models` 能明确标出"未配车道 = 不可调用"。
- 代价：新增模型需要显式建车道（控制台「新建车道」或 `PUT /api/lanes/{name}`），不再是零配置。
- 代价：ADR 0001 的"响应 `model` 回填请求名"仍然必须保留（改名依然存在）。
