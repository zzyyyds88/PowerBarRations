# ADR 0012: 出站准入控制（在飞上限 + 每分钟请求数 + 有界 FIFO 排队）

- 状态：已采纳（2026-11-23）
- 依据：`docs/routing-spec-v1.md` §3.2、§4.1、§4.2；`docs/api-spec-v1.md` §4.1、§4.4；`docs/ui-spec-v2.md` §9.1
- 关联：[ADR 0002](0002-fast-fail-503.md)

## 背景

上游配额差异很大：有的按账号或模型的**同时请求数**限流，有的按**每分钟请求数**限流，超限时用
429 或 400 承载失败。PBR 此前只有**事后**机制：请求全部直接发往上游，撞到 429 之后才按
`soft_rate_limit` 重试同一成员并写冷却；`member_max_attempts > 1` 还会在限流窗口内
原地再打一次，等于给限流添柴。单成员车道上，一次十几秒的上游抖动会被放大成约一分钟的 503。

生产实证（2026-11-23，基于 6000 条线上日志的离线回放）：

- `1412 / deepseek-v4.1-flash`：`429, maximum 12 requests in 1 minutes`，峰值 RPM **16** > 上限 12；
  并发维度全程 1~9、失败率 0.1%——**是 RPM 超限，不是并发超限**；
- `基元律动192 / egg-alpha-004`：失败率 20.2%，但**在飞数为 1 时同样 18%**，同秒内既有成功又有失败，
  失败请求中位耗时 5.9s（成功 7.0s）——是上游随机故障，**与并发无关**；
- 全站在飞数峰值仅 9，`1412` 的 p95 并发为 4。

因此：**默认不限制**（`0`），限流按渠道显式开启；开启后按上述实测，RPM 轴收益最大、
延迟代价最小（并发压到 2 会让 44%~61% 的请求排队，平均等待 2~8 分钟）。

参考实现（`reference/magpie`，本地 agent 网关，与本项目用法最接近）的做法是：
每个 provider / key / account 的 `MaxConcurrency`（**在飞请求数**）+ FIFO 队列 +
`QueueLimit` / `QueueWait`，另有独立的 `MaxRPM`（每分钟请求数）作为**第二轴**，两者共用
"就绪判定"与队列；注释明确 "Waiting is not failing" 与 "the vendor sees no more than that many"。
它同样默认不限制，只在用户显式配置时启用。

## 决策

1. **两个正交的上限 + 一个自适应模式**，都配在 `(channelId, member.Model)` 上：
   - `max_concurrency`：同时在上游的请求数（在飞口径，不是到达速率）；
   - `max_rpm`：任意滑动 60 秒窗口内的上游尝试次数；
   - **`max_concurrency: -1` = 自适应**（AIMD）：上限由运行态自己学，用户不填数字。
   两个固定上限都要满足才算"就绪"（对齐 magpie 的 `ready() = lanes.free() && rpms.free()`）。
   理由：并发压不住"12 次/分钟"这类窗口配额，RPM 也压不住"同时在跑 6 个"这类并发限制；
   生产里两类都实际发生过。
2. **作用域 = `(channelId, member.Model)`**，进程内全局共享（跨车道、跨成员组）。
   配置挂在渠道上、按渠道声明的模型名寻址（与 `prices` 同口径）。同一账号下不同模型可以有
   不同上限（实测同一账号一个模型被限、另一个正常），所以不按账号一刀切。
3. **配置**（`Channel.Setting.pbr_rate_limits`，与 `pbr_prices` 同构，不改 schema）：
   `{model, max_concurrency, max_rpm, queue_limit, queue_wait_seconds}`。
   两个固定上限为 `0` = 不限制（**默认**，依据上节实测）；`max_concurrency = -1` 启用自适应。
4. **自适应算法（AIMD + 延迟辅助，`max_concurrency = -1` 时生效）**：

   | 事件 | 动作 |
   |---|---|
   | 成功且当时已打满当前 `limit` | `limit += 1/limit`（加性增长，越大涨得越慢） |
   | 429 / 明确的并发限流报文 | `limit = max(1, floor(limit × 0.5))`，该成员暂停 1 秒 |
   | TTFT > 2× 基线且已打满 | `limit = max(1, floor(limit × 0.9))` |
   | `timeout` | `limit = max(1, floor(limit × 0.9))`，不暂停 |
   | 5xx / 普通 4xx | 不动 `limit`（不是拥塞信号） |
   | 成功 | 更新 TTFT 基线（低分位 EWMA） |
   | 连续 5 分钟无请求 | `limit` 向初始值衰减（每次减半） |

   边界：初始 `max(2, ceiling/8)`、下限 `1`（绝不降到 0，否则无法恢复）、
   上限 `adaptive_ceiling`（默认 32）。基线取最近成功请求 TTFT 的 p50 EWMA（α=0.2）。
   运行态进程内保存，重启回初始值。
5. **429 = 减速，不是故障**（2026-11-23 裁决，routing-spec §4.1.1）：429 的语义是"你发太多"
   而非"我坏了"；把它当成员故障写冷却，会让"网关自己超发"冻结整条车道（单成员车道直接 503）。
   因此 **`soft_rate_limit` 一律不写 `Cooldowns`、不计熔断分、不发 `cooldown` 事件**，
   改为写 `PacedUntil` 减速（`Retry-After` 优先，否则 3s，上限 60s），成员仍 `available=true`。
   这与是否启用限流无关——是错误分类语义的修正，对全部成员生效。
   `hard_quota`（欠费/额度关键词命中）仍走长冷却：那是账号状态，与并发无关。
6. **准入顺序**（对齐 magpie "a full one gives way first"）：
   1. 按车道优先级找"现在就绪"（空槽且窗口未满）的成员，有就直接发
      （低优先级但就绪的成员可以顶上）；
   2. 都不就绪 → 排在**预计最早就绪**的成员队列（并列取排队人数少者、再并列取优先级高者），
      FIFO 等待，上限 `queue_wait_seconds`；"最早就绪"取 `max(槽位空出估计, 窗口滑出估计)`；
   3. 等待超界或队列满 → 换下一个成员再试；
   4. 全部耗尽 → **429 + `Retry-After`**（本地配额，不是车道不可用），
      `Retry-After` 取最早就绪估计（至少 1 秒）。
7. **槽位与计数的生命周期**：槽位从"即将发往上游"持有到响应读完 / 流结束 / 失败 / 取消；
   RPM 计数在**发出上游请求时**记 1 次（与槽位同时），不因失败回滚（上游已经收到了）。
   同成员重试的间隔不占槽、不占 RPM；客户端断开时排队中的请求立即出队，
   不发上游、不计失败、不计 RPM。
8. **排队与节流不是成员失败**：不写冷却、不计熔断分、不改成员 `last_error_kind`。
   503 `No available channel` 仍只表示"车道真正不可用"（冷却/熔断/人工停用），
   本地排队超界用 429，两者不混。
9. **探活与渠道测试不排队、不计 RPM**：人工低频，且必须反映上游真实状态。
10. **对上游随机故障不做假承诺**：实测 `egg-alpha-004` 在并发 1 时仍有 18% 失败，
    限流无法改善。这类渠道的正确处置是加兜底成员（同厂商另一模型），不是调限流参数。

## 后果

- 渠道对象新增 `rate_limits`（读回、写校验、导出/导入、控制台渠道编辑器）。
- 模型面新增一种**本地 429**（+ `Retry-After`）：日志 `error_kind=local_throttle`，
  attempts 链含 `throttled` 状态与 `wait_ms`；成员运行态的 `last_error_kind` 不出现该值。
- **`soft_rate_limit` 语义变更（对全部成员生效，不依赖是否启用限流）**：不再写冷却、
  不计熔断分、不发 `cooldown` 事件，改为 `PacedUntil` + `member_paced` 事件。
  健康快照新增 `paced_until` 字段；`circuit_allowed_fails` 里的 `soft_rate_limit` 键失效。
  这是**行为契约变更**，需在 CHANGELOG 与 README 的升级说明中写明。
- 运行态进程内保存，重启清空（与冷却/熔断一致）；探活不计入。
- 新增单测：槽位/排队/超时/取消/跨车道共享/让给就绪成员/RPM 窗口滑动与就绪判定/
  AIMD 增减与边界（下限 1、上限 ceiling）/TTFT 基线更新与延迟降档/5 分钟空闲衰减/
  **429 只写 `PacedUntil` 不写 `Cooldowns`**/**`Retry-After` 超上限时原样透传**/
  **关键词优先（429+欠费词仍归 `hard_quota`）**；
  L2 加一条节流生效用例（并发与 RPM 各一）。
- **明确不做**：TPM / 按 token 限速、跨节点共享、状态持久化、按车道覆盖。
- 与 ADR 0002 的边界：ADR 0002 管"上游不可用 → 快抛"；本 ADR 等的是"本地配额"，
  上游本身健康，等待有明确上界，超界后返回 429 而不是 503。
