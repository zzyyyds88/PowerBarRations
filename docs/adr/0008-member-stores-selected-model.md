# ADR 0008：成员只存所选模型，上游真名一律由渠道映射推导

- 状态：已采纳
- 依据：`docs/design-v1.md` §3.1、§7.1、§7.7；`docs/routing-spec-v1.md` §1.1、§1.2；`docs/api-spec-v1.md` §4.2、§5.2、§5.7；`docs/ui-spec-v1.md` §6.3
- 修订：[ADR 0005](0005-lane-required-and-channel-model-mapping.md) 决策 2/3（渠道映射的定位与查表键）、[ADR 0006](0006-lane-free-member-composition.md) §2/§5（成员唯一键、"加入时物化写入映射"）

## 背景

控制台的成员编排器里，每个成员行都有一个"上游真名"输入框（placeholder「使用渠道映射」）。实测发现三件事：

1. **该输入框与渠道级 `model_mapping` 职责重叠**。上游改名本应在渠道配置一次
   （ADR 0005 决策 2 原话："上游改名在渠道配置一次"），成员级再开一个入口等于同一
   能力两个来源；用户看到三行都填满上游名时会认为"我已经从左边选了模型，为什么还要再写一遍"。
2. **加入成员时把渠道映射"物化"写进了成员字段**（ADR 0006 §5 明确要求显式写入）。
   写进去之后它就命中了解析的第一层（非空且 ≠ 路由键），**渠道映射再改也不会生效**。
   实测：成员先落 `vendor/v1`，把渠道映射改成 `vendor/v2` 后最终上游仍是 `vendor/v1`，
   "配一次"的承诺落空。
3. **加入时与运行期的查表键不一致（真 bug）**。加入时以「成员所选模型」为键查映射
   （ADR 0006 §5），运行期却以「路由键」为键查（`effectiveUpstreamModel`）。普通车道
   两者恰好相等所以看不出；**池化车道**（车道名 ≠ 成员模型名）必然查错：实测成员留空时
   运行期解析出 `mapping[路由键]`，而界面上显示的是 `mapping[所选模型]`。
   ADR 0006 §5 自身前后两句话也互相矛盾（既说以成员所选模型为键，又说运行期以路由键为准）。

根因：**成员表只存了解析后的真名，没有存"用户选的是哪个模型"**，于是"跟随渠道映射"
在池化车道下无法实现——这不是代码没写好，是数据模型缺一层信息。

## 决策

1. **成员只存"所选模型"**。`lane_members` 的模型列语义改为"该成员所选、由该渠道声明的
   模型名"（列名 `upstream_model` → `model`）。**成员级上游名覆盖能力整体移除**：不再有
   `upstream_override`，写端点不再接受成员级真名。
2. **上游真名一律由推导得出**，单处规则：

   ```
   上游真名 = Channel.ModelMapping[成员所选模型] ?? 成员所选模型
   ```

   查表键恒为**成员所选模型**，与路由键无关（修正背景第 3 条的真 bug）。
3. **成员唯一键 = `(渠道, 所选模型)`**。同一渠道的同一模型在一条车道内**只能出现一次**，
   重复提交返回 `422 duplicate_member`；同一渠道的**不同**模型仍可多次出现（ADR 0006 §2 的
   "同渠道多成员"能力保留）。
4. **接口形状**：
   - 写：成员 `{channel, model, priority, public_alias, enabled, overrides}`。
   - 读：成员 `{channel, model, upstream_model, priority, public_alias, enabled, overrides, member_id}`；
     `upstream_model` 是**只读派生值**（第 2 条算出的真名），供展示与排障，**不可写回**。
   - `manual` 的 `active_member` 标签由 `channel/上游真名` 改为 **`channel/所选模型`**
     （成员身份稳定，不随渠道映射改动而失效）。
5. **控制台**：成员行的上游名输入框改为**只读文本**（"解析后的上游"）；左栏候选对
   **已加入的 `(渠道, 模型)` 直接禁用**，从源头上杜绝重复成员。
6. **存量数据迁移（行为保持）**：逐成员反查所属渠道的 `model_mapping`——
   - 当前值命中某个映射**右值** → 写回对应**左键**（该成员原本就是由这个模型映射来的）；
   - 未命中 → 原值写回（该值本就是模型名或用户手填的真名，推导结果不变）；
   - 空值 → 写回车道路由键（复现旧的"回落到 `mapping[路由键]`"行为）。

   三种情形下推导结果都与迁移前一致；仅在"当前值恰好又是映射左键"的碰撞情形下会变化，
   这属于新口径下的正确结果。`lanes.active_member` 同步由 `channel/真名` 重写为 `channel/模型`。

## 后果

- 优点：上游改名回到"渠道配置一次、处处生效"；池化车道的查表键正确；成员行不再要求用户
  写第二遍；成员身份 `(渠道, 模型)` 稳定，不随映射改动漂移。
- 代价：破坏性契约变更（写端点成员字段 `upstream_model` → `model`；读端点去掉
  `upstream_override`），一次性迁移 `lane_members` 与 `lanes.active_member`。
  本项目无对外兼容包袱（单用户自用、无旧系统迁移，design §11/§16.4），
  **不做双写、不保留旧字段兼容入口**。
- 不变：车道仍是唯一路由入口；没有同名启用车道一律 `503`；声明模型绝不自动建车道
  （ADR 0005/0006）；成员候选 = 任意启用渠道的任意已声明模型（ADR 0006 §2），
  本次只去掉"成员级再改名"这一层。
- 明确不做：不引入成员级 `weight`；不恢复 `weighted` / `round_robin`；不给成员加第二套改名路径。
