# ADR 0001：路由键就是模型名，显式车道降级为可选覆盖层

- 状态：部分取代——"隐式链零配置可路由"由 [ADR 0005](0005-lane-required-and-channel-model-mapping.md) 取代；"路由键 = 模型名"与"同形 503"仍然有效
- 依据：`docs/design-v1.md` §0 第 8 条、§3.1；`docs/routing-spec-v1.md` §1.1

## 背景

旧的两层网关把"分组/车道"当作必须先创建的对象：下游请求模型名 → 网关按分组选成员 →
厂商层再用 `model_mapping` 把请求名改成真名。结果是"新上一个模型"要同时改两处配置，
而且任一处漏配就表现为"模型找不到"，与"上游全挂"看起来不一样，下游必须分支处理。

## 决策

**请求体里的 `model` 就是路由键**：渠道声明 `models` 后这些模型名立刻可路由，
网关按渠道 `priority`（数字大者优先）自动排成故障链。显式车道保留，但只作为
**可选覆盖层**，用于三件事：自定义顺序、成员改名、把不同上游的不同模型名池化到一个名字下。

同时规定：没有任何渠道声明该模型时，返回与"成员全部耗尽"**同形**的
`503 No available channel for model <X>`。

## 后果

- 优点：新增模型只改一处（渠道的 `models`）；下游只需一个分支（503 即换网关重试）。
- 代价：请求名与上游真名解耦后，响应里的 `model` 必须显式回填请求名，否则上游真名会泄漏
  给下游（已在 `relay/helper/response_model.go` 统一处理）。
- 代价：模型名写错与上游全挂对下游不可区分。这是刻意取舍——下游无需分支比"能区分
  配置错误与运行故障"更重要，因为配置错误在管理面 `GET /routes/{model}` 一查便知。
