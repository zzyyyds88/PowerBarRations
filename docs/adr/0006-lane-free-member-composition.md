# ADR 0006：车道成员自由编排（任意渠道 × 任意模型），且声明模型绝不自动建车道

- 状态：已采纳
- 依据：`docs/design-v1.md` §3.1、§7.1、§7.7；`docs/routing-spec-v1.md` §1.1；`docs/ui-spec-v1.md` §6.3
- 补充：ADR 0005（不推翻"车道唯一入口"与"绝不隐式成链"），取代其中"候选成员 = 声明/映射了该路由键的渠道"这一收窄口径
- 修订：ADR 0007 收窄了本 ADR 的**展示口径**（`/routes` 只列真实车道，未配车道路由键不再以卡片出现）；本 ADR 的成员候选范围与"声明模型不自动建车道"决策不变

## 背景

ADR 0005 确立了"车道是唯一路由入口、删除隐式成链"，这是对的，保留。但它在落地时把
**成员候选范围**收窄成了"声明了该路由键（或 `model_mapping` 映射了该键）的渠道"：
控制台「新建车道 / 编辑成员链」只列出这些渠道，且新建车道在没有任何渠道声明该键时
连保存都被拦截。

这带来两个与既定产品目标直接冲突的后果：

1. **"池化"名存实亡**。`design-v1.md` §3.2、`ADR 0001`、`README` 都承诺车道能把
   "不同上游的不同模型名池化到一个名字下"（例如对外暴露 `fast`，成员分别是
   渠道 A 的 `vendor-a/model-1` 与渠道 B 的 `vendor-b/model-2`）。但在"候选 = 键匹配"
   下，用户必须先给每个渠道手工声明或映射 `fast` 这个键，才能在界面上把它选进车道；
   直接组链做不到，能力被 UI 限死（后端 `PUT /lanes/{name}` 本就不校验键匹配）。
2. **与线上 octopus 的自由度不一致**。线上章鱼的分组项直接引用 `ChannelModel`
   （渠道 + 模型），一条分组可任选任意渠道的任意模型。PBR 的车道数据模型
   `(渠道, 上游真名, 顺序)` 完全支持同样的自由，只是候选来源被收窄。

同时必须明确一条**不变**的产品决定：**给渠道声明/新增模型后，绝不自动生成车道**。
这一点 ADR 0005 已定（"删除隐式成链"、"一键固化 `POST /lanes/seed` 已整体移除"），
本次重申并写死，避免"既然候选放开了，是不是顺手自动建一条"的误读。

## 决策

### 1. 声明模型不自动建车道（重申 ADR 0005，不可回退）

- 渠道 `models` 的增删（含 `sync-models`、探测上游、手工编辑）**只改渠道声明**，
  不创建、不修改、不删除任何车道。
- 新建渠道、渠道新增模型后，该模型在路由页以 `source: unconfigured`、`routable: false`
  出现，**必须由人工显式建车道后才可调用**；未建车道一律 `503`。
- 不重新引入 `POST /api/lanes/seed` 或任何等价的批量/自动固化入口。

### 2. 成员候选范围 = 任意启用渠道的任意已声明模型

- 一条车道的成员可以来自**任意渠道、任意上游模型**，不要求这些模型声明了该路由键，
  也不要求彼此同名。成员唯一键 = **`(渠道, 上游真名)`**。
- **同一渠道可在一条车道中出现多次**（各自对应不同上游模型）：例如车道 `fast` 的成员
  可以是"渠道 A 的 `a-model-1`"与"渠道 A 的 `a-model-2`"。去重按 `(渠道, 上游真名)`，
  不再按渠道去重。
- 路由键与成员上游真名彻底解耦：对外模型名（车道名）由人工命名，成员各自指定上游真名；
  这正是"池化不同上游的不同模型名"的正式口径。

### 3. 候选清单数据来源：复用 `GET /api/channels`

- 前端从 `GET /api/v1/channels`（已返回每个渠道的 `models`）拼装"渠道 → 模型"目录，
  作为成员选择器的数据源；**不新增专用只读端点**。
- `GET /api/routes/{model}` 的 `members` 仍是该车道的真实成员链；`candidates` 字段保留，
  但**语义降级为"推荐项"**（声明或映射了该路由键、且不在成员链里的渠道），供界面排序/高亮，
  **不再作为可选范围限制**。
- 前端不得把"键匹配"当作成员可选性的判据。

### 4. 控制台：octopus 式自由编排

- **`/routes` 页整体改为卡片式**（对齐线上 octopus 分组页）：以卡片网格展示车道，
  卡片上直接呈现成员顺序与运行态；新建/编辑进入**两栏编排器**。
  （**修订**：[ADR 0007](0007-routes-lists-lanes-only.md) 进一步限定只展示真实车道，
  渠道声明但未配车道的路由键不再以卡片出现。）
- **成员编排器（新建车道 / 编辑成员链同一组件）两栏布局**：
  - 左栏「添加成员」：按渠道折叠的"渠道 → 模型"选择器（带搜索框）；点某个模型即把
    "`该渠道 × 该模型`"加入右侧已选列表。
  - 右栏「成员（顺序）」：已选成员的有序列表，支持**拖拽或上移/下移**排序、删除、
    编辑上游真名（清空 = 用渠道映射），并提供「清空」。
- **不提供「自动添加」**：全部成员由人工逐个挑选，符合"路由只支持手动维护"的产品要求。
- 输入的路由键**不要求**任何渠道声明过；候选为空时仍可保存——只要已选成员非空。
  保存即 `PUT /api/lanes/{name}`，成员顺序即优先级（首位最大）。

### 5. 成员上游真名默认值

- 从"渠道 X → 模型 m"加入成员时，默认**按渠道 `model_mapping` 解析 m**，并把解析结果
  （有映射 = 映射右值；无映射 = `m` 本身）**显式写入**该成员的 `upstream_model`。
  这样**池化车道**（车道名 ≠ 成员模型名，例如车道 `111` 里选 `glm-5.3-flash`）
  也能正确命中映射；用户仍可手动改写或清空该字段。
- **映射查表以「成员所选模型 m」为键，不是以车道名/路由键为键**：车道名可任意命名，
  与映射键无关；只有车道名恰好等于映射键时，运行期回落才会命中同一条映射。
- 运行期解析优先级不变：成员级 `upstream_model`（非空且 ≠ 路由键）> 渠道 `model_mapping` > 路由键。

## 后果

- 优点：`/routes` 页能完整表达车道数据模型的自由度，"池化"从文档承诺变成可操作能力；
  与线上 octopus 的分组心智一致，迁移/排障成本低。
- 优点：路由键与上游真名解耦后，下游看到的模型名可完全由部署方命名，不再被迫与上游同名。
- 代价：候选放开后，用户可以把明显不相关的模型组进一条车道；这是刻意的——单用户自用网关
  信任运维者，不为"防呆"牺牲自由度。
- 代价：成员去重从"按渠道"改为"按 (渠道, 上游真名)"，前端已有实现与测试需同步调整；
  同一渠道在一条车道多次出现时，manual 模式的 `active_member` 标签
  `channel/upstream_model` 仍唯一。
- 不变：车道仍是唯一路由入口；没有车道一律 `503`；声明模型绝不自动建车道。
